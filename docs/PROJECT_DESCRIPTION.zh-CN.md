# AgentX FindBack：给录像装上记忆

> 一句话：在固定机位的录像或实时画面里登记一件物品，然后直接问“它在哪、什么时候不见的”。每个位置回答都带录像时间和可回放的原始画面；证据不够时，系统明确说“无法确认”，绝不猜。全部模型运行在一台 NVIDIA DGX Spark 上。

英文完整说明见 [README](../README.md)，演示视频与开发文章的链接见 README 的 Submission 一节。本项目以 [Apache-2.0](../LICENSE) 开源。

## 一、作品特点与亮点

**解决的问题。** 家里的钥匙、实验室的样品、工位上的工具，放下就忘了在哪。固定摄像头其实全程都看见了，但要从录像里找到答案，只能一帧一帧地拖。FindBack 让用户在录像中框选一次、登记一件物品，之后用自然语言提问，系统从逐时刻的对象记忆里给出答案，并附上可以一键回放的原始帧。

**与“视频问答”的区别。** FindBack 不做全片摘要或跨视频搜索，而是为用户登记的物品维护一份带时间戳、不可改写的观测记忆，并严格区分三件事：“截止时刻能看到它”“它最后一次被确认是在何时何处”“当前无法确认”。录像只能描述录像本身，系统从不声称知道物品在现实世界中的“现在”位置。

**五个亮点：**

1. **每个位置都有证据。** 位置回答必须引用一条真实观测；代码逐项复核录像、物品、记忆版本、观测编号和提问截止时间，模型引用了未检索到的证据会被删除并显示告警。
2. **不确定就明说。** 物品被拿走、被遮挡或与相似物品身份冲突时，回答保留“最后一次确认”的时间和画面，并标明当前位置未被确认。在五段冻结问题的公开桌面录像上，11/11 个问题全部答对，零个错误位置。
3. **多智能体各司其职。** Nemotron 规划智能体调用有界的记忆工具；Cosmos-Reason2 作为第二个智能体做视觉复核，意见单独保存、只作参考；SAM 2.1、DINOv2、RT-DETR 在 CUDA 上构建记忆；最终由代码裁决。
4. **Skills 是可评测、可签名的交付物。** 6 个带版本的应用 Skill 约束智能体的每一步；2 个可移植 Skill 和一个 MCP 服务让 Claude Code、Codex、OpenClaw 等外部智能体也能查询记忆、审计证据。留出测试中，两个编程智能体安装 Skill 后正例都从 1/15 提升到 15/15。
5. **可离线复核。** 任一回答可导出离线证据报告（原始帧、记忆来源、Skill 与工具轨迹、SHA-256 清单和只依赖 Python 标准库的校验脚本），不连服务器也能验证。

## 二、技术方案与架构

```
录像 / 实时画面 ──► 感知（CUDA：SAM 2.1 · DINOv2 · RT-DETR）──► 版本化对象记忆（观测 · 事件 · SQLite）
                                                                        │ 记忆工具
问题 + 截止时间 ──► 规划智能体（Nemotron 3.5 Lightning · NVFP4 · vLLM）◄─► 6 个应用 Skills
                         ▲ 仅供参考                                      │ 提议
              视觉复核智能体（Cosmos-Reason2-8B）                 代码校验：来源 · 物品 · 版本 · 时间
                                                                        ▼
                                                        回答 + 原始帧引用 + 离线证据报告
```

- **登记与记忆构建。** 用户在某一帧框选物品（也可让 RT-DETR 或 Cosmos 给出候选，但必须人工确认）。SAM 2.1 以登记框为提示，按每秒 5 帧因果地跟踪；DINOv2 在外观不一致时拒绝接受跟踪结果；RT-DETR 发现多个同类候选时，记忆写入“身份待确认”而不是猜一个。每次构建生成一个不可改写的记忆版本，后来的登记不会伪造更早的观测。
- **提问与规划。** Nemotron 规划智能体最多 8 步，只能调用固定的工具：列出物品、按条件查找、读取某时刻状态、读取历史、查看某条观测、请求一次视觉复核。它提议“哪个物品、什么意图、引用哪些观测”，最终文字由代码从已保存的观测渲染。无效调用、重复调用或步数超限都会以可见的回退结束。
- **视觉复核。** Cosmos-Reason2-8B 对选定原始帧逐帧定位（每帧单独提问、时序由代码负责），结果与权威记忆分开保存。演示录制中它曾把已被拿走的手机描述为“没被动过”，而它自己引用的帧里手机已不在；记忆回答（最后确认于 13.4 秒）不受影响——这正是复核只作参考的原因。
- **实时模式。** 浏览器摄像头（或 `agentx live-push` 推流）以每秒 5 帧写入一段不断增长的分片 MP4，记忆边录边建；停止时封存并计算 SHA-256，封存后离线重建与实时结果逐条一致。

## 三、智能体与 Agent Skills 设计

- **应用 Skills（6 个）：** 观测策略 `observe-object-events`、历史检索 `retrieve-object-history`、物品选择 `compile-object-selection`、工具使用 `answer-with-memory-tools`、证据校验 `verify-location-answer`、视觉复核 `review-visual-evidence`。由代码按步骤路由加载，每次回答记录所用 Skill 的 SHA-256 与完整工具轨迹。每个 Skill 目录包含 SKILL.md（路由与负触发）、Skill Card、评测用例、BENCHMARK 与签名，参照 NVIDIA Verified Skills 的目录规范组织（团队自测，并非 NVIDIA 认证）。
- **可移植 Skills（2 个）与 MCP：** `findback-video-memory` 让外部智能体列录像、提问、取证据，缺少录像、物品或截止时间时先追问，并规定录像不能证明“现在”的位置、令牌绝不输出；`findback-evidence-audit` 在无网络时审计证据 ZIP。服务器为外部智能体提供只读+提问令牌，写操作一律拒绝。
- **实测而非断言：** Claude Code 与 Codex 在三组冻结的留出提示上，正例从 1/15 提升到 15/15（每个智能体配对 14–0，McNemar p≈0.0001）；30 次负例运行中 1 次误触发，200 次运行零令牌泄露。内部消融显示 Skills 减少了无效计划（36→25），但在留出集上没有额外的正确率增益——我们如实保留这个中性结论。

## 四、部署说明（一台 DGX Spark）

| 组件 | 部署方式 |
| --- | --- |
| 平台 | NVIDIA DGX Spark（GB10 Grace Blackwell，aarch64），CUDA 13.0，驱动 580.142，PyTorch 2.14.0+cu130，vLLM 0.28.0 |
| 规划模型 | 主办方提供的 ModelOpt NVFP4 检查点 Nemotron-3.5-Lightning-30B-A3B（权重 17.86 GiB），vLLM 服务名 `nemotron`，仅监听 127.0.0.1:8000，上下文 32768，最大并发 8，`--reasoning-parser nemotron_v3`，显存比例 0.3 |
| 视觉复核模型 | Cosmos-Reason2-8B（ModelScope `nv-community`），BF16，127.0.0.1:8002，上下文 16384，每请求最多 8 张图，最大并发 4，显存比例 0.3；同一进程挂载团队训练的 LoRA `findback-grounding-v1`（rank 16，可选） |
| 感知 | SAM 2.1 Small（BF16，CUDA，32 帧记忆、帧缓存上限 34）、DINOv2-small 外观校验、RT-DETR R18 相似物干扰防护，每秒 5 帧采样 |
| 应用 | Python/FastAPI + SQLAlchemy/Alembic + SQLite，Svelte/TypeScript 前端，FFmpeg；单进程，127.0.0.1:9000，tmux 托管 |

部署步骤：从 ModelScope 下载并校验模型哈希 → 用 `scripts/spark/start_model_services.sh` **串行**启动两个 vLLM 服务并等待 `/v1/models` 就绪（统一内存上的显存比例是对全部内存的比例、需要相加计算；另一个 vLLM 初始化时启停服务会触发内存剖析断言）→ `agentx doctor --probe` 检查 GPU、模型端点与权重 → 启动应用。外部智能体通过可移植 Skill、MCP 服务或 OpenClaw 访问应用，使用只读+提问令牌。完整步骤见[部署指南](DEPLOYMENT.md#spark-competition-profile)。

## 五、模型与智能体优化

所有优化都先冻结门槛、再在同一会话里跑对照两组，失败也保留。

- **选型与显存预算：** 选用 30B-A3B MoE 的 NVFP4 检查点（每 token 约 3B 激活参数），让规划模型、Cosmos 和 SAM 2.1 同时常驻 GB10 统一内存（实测两个 vLLM 引擎约 37.0 GB 与 34.6 GB，感知进程 1.4 GB）。
- **CUDA 掩码后处理：** 把 SAM 2.1 的掩码几何计算改为 GPU 上的精确整数归约并批量传输存在分数：1080p、4 个掩码时该环节 21.1 → 1.75 毫秒（12.08×，4K 为 12.19×）；3 段 LaSOT 视频的完整索引快 2.8%，3 轮配对运行 831/831 条预测逐行一致。
- **SAM 2.1 状态留在 GPU：** 利用统一内存把记忆库留在 GPU，每帧快 10–16%，检测结果哈希完全一致；SAM 2.1 Large 因相似物跟踪更差（117/225 → 27/225）且更慢被否决。
- **Cosmos 复核：** 8 帧一次性提问方向判断错误，改为逐帧定位 + 参考裁剪图 + 代码负责时序后逐帧正确；0–1000 整数坐标与 768 像素输入把瓶子集命中从 46/165 提升到 126/165；8 路并发把每个 8 帧窗口从 6.73 秒降到 4.16 秒（−38%）。
- **在 GB10 上微调 Cosmos-Reason2-8B（LoRA）：** rank 16、4,364 万可训练参数，5,000 个 GOT-10k 衍生样本，4 小时 33 分，峰值 27 GiB（进程显存上限 0.55）。v1 把留出集定位命中从 297/408 提升到 356/408，但缺席帧误报从 5/18 升到 9/18，未通过训练前冻结的门槛，不替换基座；v2 与困难负例 v3 同样未通过。只有“基座判存在 + v1 给定位点”的组合在 10 段新瓶子视频上通过门槛（命中 167→185/240、跨录像误报 86→75/240），作为可选模式上线。
- **量化与模板：** Cosmos FP8 量化把权重从 16.74 GiB 降到 10.04 GiB，但开发集少对 14 个点，保持 BF16；阶跃星辰 Step3-VL-10B 默认模板总先“思考”，单帧 110.7 秒、1,525 token，定制免思考模板后 3.3 秒。
- **规划器与语言：** 132 例真实 Nemotron 语言回归中应用通过 131/132、模型答对 129/132，修复后受影响的 60 例全部通过、零回退，零错选物品；两次注入的无效计划均被代码拒绝后由模型修正。

## 六、技术栈

- **NVIDIA 平台与 SDK：** DGX Spark GB10 统一内存、CUDA 13 / PyTorch cu130（含自定义 GPU 掩码归约）、vLLM 服务 NVFP4 与 BF16 模型并挂载 LoRA、PEFT LoRA 训练、NVIDIA Verified Skills 目录规范、NVIDIA SkillSpector（Skill 安全扫描）、与 NVIDIA VSS Skills 同列的路由评测。
- **NVIDIA 模型：** Nemotron 3.5 Lightning 30B-A3B NVFP4（线上规划器）、Cosmos-Reason2-8B（线上视觉复核、候选与定位）、团队 LoRA 适配器（可选）、Cosmos3-Nano（同场评测，留出集 352/408）、Cosmos-Reason2-2B（支持低内存主机）。
- **阶跃星辰模型：** Step3-VL-10B 在 Spark 上以 vLLM 本地部署并参与复核模型对比（开发集 249/366）；Step-3.7-Flash 作为可选规划器（低推理强度下 28/28、11/11，零回退，与 Nemotron 持平）和外层 Skill 智能体（路由首动作 21/22，并在 OpenClaw 中完成查询）。线上保留本地 Nemotron，推理全部在 Spark 上完成。
- **其他开源模型与框架：** SAM 2.1、DINOv2、RT-DETR；FastAPI、SQLAlchemy、Alembic、SQLite、Svelte、FFmpeg、MCP。

## 八、局限

演示素材是 Pexels 授权库存视频，不是团队自拍，也不是摄像头直播；尚未完成真实用户对照实验，因此不宣称节省时间或普遍准确率。外观高度相似的物品发生碰撞后召回仍低，系统此时选择“身份待确认”而不是猜。视觉复核模型会出错，所以只作参考。实时模式验证范围是 1–2 个物品、每秒 5 帧、单客户端。
